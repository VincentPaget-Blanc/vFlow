## Frozen boundaries for this cycle

No silent changes to gate membership, denominators, transforms, FCS decoding, serialization, lineage, exports, interaction ordering/failure semantics, cache-visible behavior, deterministic rendering/order, or AP01–AP07 performance architecture. BR01/BR05/BR06/BR07/BR08/BR09/BR10/BR11 interaction/failure-order contracts remain binding.

## Planned sequence

1. Move the embedded historical changelog (documentation-only; not an architectural win).
2. Extract remaining pure auto-gate and multi-gate statistics computation.
3. Extract a composed `BatchStatsRunner`.
4. Extract a composed `GateInteractionController`.
5. Introduce `RenderPlan` / `FlowRenderer` ownership boundary.
6. Reassess and stop when the next extraction mainly moves glue or increases indirection.

## Milestone 3 — composed BatchStatsRunner

Added `vflow.services.batch_stats_runner.BatchStatsRunner` with explicit request/result/adapters. `FlowApp.batch_export_stats()` now owns only preflight validation, the Tk dialog, narrow host adapters, and completion dialogs/status. The runner owns:

- recursive target discovery/exclusion;
- per-file fresh disk loading orchestration;
- lineage replay and current-transform finite-event filtering;
- gate-region evaluation/row assembly;
- CSV and exclusion/error-log writing;
- structured terminal outcomes.

The fresh-read adapter deliberately preserves alias application before case normalization, and the gate callback deliberately bypasses the interactive persistent mask cache. Five runner characterization tests cover end-to-end CSV/log output, progress order, alias ambiguity classification, lineage denominator filtering, and terminal-outcome distinctions.

### Recorded strange behavior, preserved

The v4.2.0 Batch Stats workflow evaluates every applied gate against a dummy one-event `[0.0], [0.0]` input and builds a `region_cols` list that is never consumed. Because the calls can expose cache/evaluation failure ordering, v4.3 preserves this dummy pass inside `BatchStatsRunner` and characterizes that it occurs before lineage construction and file loading. It is **not** opportunistically removed.

## Milestone 4 — composed GateInteractionController

Added `vflow.controllers.gate_interaction_controller.GateInteractionController` and changed the legacy `FlowApp` event surface to lazy composed delegation:

- `_on_click`: 215 → 2 physical lines;
- `_on_motion`: 300 → 2 physical lines;
- `_on_release`: 175 → 2 physical lines.

The new controller owns the click/motion/release lifecycle and all of the previously certified callback ordering around handle drag, gate-body move, fresh draws, polygon interaction, hover, cursor policy, release routing, threshold materialization, and deletion/finalization. Geometry helpers, hit testing, preview rendering, cache owners, widgets, and gate-manager updates remain behind the `FlowApp` host boundary for this milestone; they were deliberately not moved simultaneously.

The extraction also centralized the BR11 failure-atomic gate-assignment snapshot/rollback primitive in `vflow.services.gate_assignment_transaction`. It deliberately uses base-`dict` reads/writes so dict-subclass failure oracles do not gain new observable hooks.

### Characterization caught during extraction

Two extraction bugs were detected before certification:

1. callbacks written as `setattr(self, ...)` after composition initially mutated the controller instead of the host; BR06 stray-hover cleanup caught this;
2. the first shared rollback helper used ordinary mapping methods and therefore changed BR11 dict-subclass failure behavior; the helper was restored to the exact base-`dict` semantics.

Both were corrected before the milestone was certified.

### Architecture-source contract migration

A subset of v4.2 tests intentionally asserted that concrete event authority remained textually inside `FlowApp`. Those assertions directly conflict with the requested v4.3 composition boundary. They were migrated—not deleted—to inspect the same concrete ordering/materialization contracts in `GateInteractionController` and to expect the explicit `host` boundary. Runtime/behavioral tests remain in place, and four new composition tests assert thin `FlowApp` delegates, lazy singleton composition, event authority ownership, and host-targeted hover mutation.

## Milestone 5 — RenderPlan / FlowRenderer

Added a composed rendering boundary under `vflow.rendering`:

- `RenderPlan`: a frozen, slots-based structural snapshot of the stable inputs materialized before a render pass (theme, active/display sets, effective gates, plot mode/style, channels and scales);
- `FlowRenderer`: owns the deterministic full-render lifecycle, cold KDE precomputation, Dot/Density/Contour/Gated drawing, marginals, GMM overlays, KDE/Otsu shading, and population-label drawing;
- `FlowApp.refresh_plot()` and the legacy `_plot_*`/label/KDE-precompute surfaces remain compatibility delegates.

Repeated Tk-variable reads whose timing is historically observable (`fit_axes`, `lock_scale`, legend/grid/label toggles) were deliberately **not** snapshotted into `RenderPlan`. They remain at their frozen v4.2 read points inside `FlowRenderer.render()`. The final render ordering remains:

`axis scale -> fit -> population labels -> legend/status -> locked limits -> minor ticks -> gate preview -> single draw_idle`.

Architecture-only AP03/AP04/AP05/AP07 assertions were migrated to the new render owner. Runtime cache/numerical tests continue to call the legacy facade and were not weakened.

3. Legend/fit/lock/grid/label Tk variables are intentionally read more than once at their historical points rather than normalized into a single snapshot.

## Milestone 6 — complete the interaction-controller ownership boundary

The Milestone 4 lifecycle extraction was intentionally conservative. The post-render reassessment showed that leaving large interaction-only helpers in `FlowApp` still split ownership across the exact subsystem identified by the handoff. A final high-value interaction slice therefore moved the concrete implementations of:

- handle enumeration/drawing/hit testing;
- gate interior and line hit testing;
- handle-pixel cache rebuild;
- hover-handle and cursor resolution;
- handle-drag geometry/cache mutation;
- preview/handle clearing;
- drag background capture/release and blitting;
- gate preview artist construction.

These implementations now live in `GateInteractionController`. The legacy `FlowApp` helper names remain thin delegates.

### Compatibility override surface preserved

The event lifecycle intentionally continues to call `host._hit_test_*`, `host._preview_gate`, `host._blit_render`, etc. rather than bypassing the facade. Several frozen behavior-review/architecture tests use instance monkeypatches or unbound `FlowApp` helper calls as failure oracles. `_gate_interaction_owner()` resolves the composed owner for normal `FlowApp` instances and creates an ephemeral owner for historical unbound/duck-typed helper calls, preserving those observable boundaries.

This was detected by characterization during extraction: directly calling the controller helper implementations from the event lifecycle bypassed monkeypatched host helpers and changed BR08-style failure ordering. The direct calls were therefore rejected before certification.

## Milestone 7 — composed ProjectDataLoadCoordinator

The post-M6 reassessment was deliberately reopened for one separately justified
final slice: the remaining project/data filesystem workflows still formed a
cohesive ownership boundary rather than arbitrary UI glue. Added
`vflow.controllers.project_data_load_coordinator.ProjectDataLoadCoordinator` as
a composed owner while retaining the historical `FlowApp` public methods as
thin compatibility facades.

The coordinator now owns:

- dataset path admission, fresh disk reads, confirmed alias reuse, case-only
  normalization, FCS compatibility/spillover notice accumulation, B27 atomic
  row-registration/commit ordering, generation/cache mutation, and post-load
  warning/resolver sequencing;
- gate-session save orchestration, exact v2 payload construction, the
  threshold-schema failure boundary, JSON writing, and completion status/dialogs;
- gate-session load orchestration, file/schema/lineage/version checks, v1/v2
  confirmation ordering, deterministic sanitization/provenance validation, Tk
  threshold-variable materialization, context binding, replacement, cache/stat
  recomputation, and final presentation sequencing;
- excluded-file list CSV save/load persistence, including the frozen distinction
  between already-excluded, currently loaded/moved, and unloaded/registered paths.

`clear_all_files`, `_exclude_file`, and `_restore_file` intentionally remain in
`FlowApp`: they are immediate file-list/widget interactions rather than
filesystem/project-load workflows. This prevents the new coordinator from
becoming a generic application helper.

### Compatibility and characterization details

The facade passes the live `filedialog`, `messagebox`, `tk.BooleanVar`, and
`get_last_folder` dependencies into the composed owner. This preserves existing
module-level monkeypatch/failure-oracle behavior used by the frozen tests and
keeps the controller import free of Tk. Historical unbound/duck-typed calls such
as `FlowApp._load_paths(harness, ...)` remain valid through the lazy
`_project_data_load_owner()` fallback.

The extraction briefly exposed a mechanical decorator risk: moving `_load_paths`
would have swallowed the neighboring `@staticmethod` on `_read_data_file` if
left unchecked. The decorator was restored before focused certification. No
runtime behavior change was accepted.

Architecture-source assertions that previously required load/save workflow text
to live in `FlowApp` were migrated to the new owner while retaining the same
ordering/error assertions. New characterization also covers thin facades,
composition rather than inheritance, and excluded-list save/load behavior.

### Stop decision

M7 removes the last remaining coherent filesystem/project-load workflow from the
monolithic controller. At **2,748 substantive lines / 18.25% of production
code**, the remaining large methods are now predominantly composition-root, Tk
presentation, interactive nomenclature, or narrow UI/status/commit shells around
already extracted services.

Further movement would primarily create adapter layers, split tightly coupled
widget choreography, or relocate small orchestration without establishing a new
independent owner. That is diminishing architectural benefit. The controller
decomposition cycle therefore **stops here**.

The runtime/package release metadata remains at the frozen v4.2.0 value during
this structural cycle. The delivered tree is externally labeled `4.3.0-dev`;
version metadata should change only in a subsequent explicit v4.3
release-cleanup/certification phase.
