# vFlow v4.3 Science-Method A2 Audit

## Status

This checkpoint is a **v4.3.0-dev scientific-method hardening cycle** built on the certified Accuracy Hardening A1 checkpoint. It deliberately addresses two methodological/interoperability issues that A1 identified but did not silently change:

1. the historical vFlow scales named `logicle` and `biexp` were signed-log approximations rather than a standards-reproducible cytometry Logicle transform; and
2. polar/vector analysis did not explicitly state whether source Y coordinates increased upward (Cartesian) or downward (image coordinates).

This cycle is **not** a silent reinterpretation of historical results. Historical transform semantics remain available exactly, and new scientific semantics require explicit provenance.

Runtime/package version metadata remains frozen at **4.2.0**. This archive is labeled externally as a v4.3.0-dev checkpoint and is not a v4.3 release certification.

## A2 decision 1 — standards Logicle is additive, not a rename

### New transform

A new canonical scale identity, `logicle_gml2`, implements the equation-based Gating-ML Logicle transform with explicit parameters:

- `T` — top of scale;
- `W` — width of the approximately linear region;
- `M` — number of decades for the positive logarithmic range;
- `A` — additional negative range.

The implementation is in `vflow/core/logicle.py`. Parameters are validated, serialized, included in compatibility checks, and incorporated in transform/render/cache keys.

The numerical forward mapping uses a vectorized Newton solve with a strict residual test and an independent monotonic bracketed solve as a fallback. The inverse mapping evaluates the modified biexponential stably around the zero location.

### Historical behavior is not reinterpreted

The historical identities remain accepted as compatibility aliases:

- old `logicle` -> explicit `legacy_logicle`;
- old `biexp` -> explicit `legacy_biexp`.

Their formulas are unchanged. No historical gate geometry is numerically converted when an old session is loaded.

New UI/session provenance uses the explicit `legacy_*` names so a future reader cannot mistake those approximations for standards Logicle/Biexp behavior.

### No claim of exact FlowJo Biex

A2 intentionally does **not** introduce an `exact_flowjo_biex` mode. Current FlowJo documentation describes its Biex display as lookup-table based, whereas Gating-ML Logicle is equation/parameter based and reproducible from `T/W/M/A`. Implementing an undocumented or guessed LUT and calling it exact would create a new accuracy risk.

## Gate-session provenance migration

Gate-session schema is advanced from version 2 to **version 3**.

### v1

Existing v1 compatibility remains frozen.

### v2 load behavior

A v2 session using `logicle`/`biexp` is normalized only at the identity/provenance level:

- `logicle` becomes `legacy_logicle`;
- `biexp` becomes `legacy_biexp`.

Gate coordinates, thresholds, vertices, and population membership are not transformed.

### v3 standard Logicle

For an axis using `logicle_gml2`, its `T/W/M/A` object is serialized with the analysis/gate context. X and Y may have independent parameter sets.

A v3 gate/context that declares `logicle_gml2` but omits the required axis parameters is rejected rather than assigned hidden defaults.

## Cross-layer transform consistency

The standards transform is threaded through:

- analysis state;
- numeric forward/inverse transforms;
- Matplotlib axis transforms;
- gate membership evaluation;
- population lineage replay;
- auto-gate transformed data and inverse threshold mapping;
- KDE density/contour payloads;
- rendering and cold-KDE precompute;
- gate-session serialization/loading;
- cache identity and eviction compatibility.

Per-axis `T/W/M/A` is part of cache provenance so changing parameters cannot reuse a payload generated in another coordinate system.

## A2 decision 2 — explicit polar Y-coordinate orientation

Polar/vector analysis now exposes two explicit choices:

- `cartesian_y_up`: source +Y points upward;
- `image_y_down`: source +Y points downward, as in the conventional upper-left image coordinate system.

The historical behavior remains the default: `cartesian_y_up`.

For `image_y_down`, vFlow reflects `dy` before `atan2` so exported/displayed angles use one documented mathematical convention:

> 0 degrees = +X; positive direction = counter-clockwise after Y-orientation normalization.

The selected orientation and angle convention are written to polar statistics exports.

A supplied unsupported orientation is rejected. There is deliberately no `auto` mode because guessing orientation from numbers alone is not scientifically defensible.

### Statistical invariants

Changing only Y orientation reflects angle direction. It does **not** alter displacement magnitude, MRL, or Rayleigh p. Mean direction changes sign/reflection as expected.

## UI changes

## Explicit limitations / non-goals

1. `logicle_gml2` is standards Logicle; it is **not** presented as exact FlowJo Biex.
2. A2 does not automatically convert historical legacy gates into standards Logicle coordinates. Such conversion would move boundaries and must be an explicit user/scientific migration operation if ever added.
3. A2 does not infer Logicle parameters from FCS metadata. Parameters are explicit to avoid hidden assumptions.
4. Selecting `image_y_down` intentionally changes reported mean direction relative to the historical Cartesian convention; that is the scientific purpose of the setting. MRL and Rayleigh significance strength are invariant under that reflection.
5. This work addresses the two known A1 methodological issues. It does not constitute a claim that no undiscovered scientific-software defects can remain.

## Structural decision

No new broad structural refactor was opened. The A2 changes were threaded through the already-composed services/controllers only where required for correct scientific provenance and cache identity.
